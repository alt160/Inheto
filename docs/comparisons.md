# Comparing serialization options

Guides supplement the [README](../README.md). Examples refer to its `Order` and `OrderLine` types unless stated otherwise.

The practical question is often not whether a serializer can eventually represent your data, but how much code and model reshaping you must supply to make that happen. Inheto combines broad built-in types, shared/circular references, inherited collections with their own members, shape-based projection, and selective binary reads without requiring serialization-specific model declarations.

The table focuses on what is not automatic, or what the developer must arrange. It describes the usual documented APIs, not every possibility achievable with custom extensions.

| Option | What is not automatic / additional developer work | What Inheto supplies for that scenario |
| --- | --- | --- |
| [System.Text.Json (.NET)](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/supported-types) | Rectangular multidimensional arrays need a converter or different representation. Shared/circular references require `ReferenceHandler.Preserve`, with limits for arrays and immutable types. Default collection handling represents elements, not a collection subclass's additional object members; retaining both needs custom handling or a wrapper. | Native multidimensional array structure, built-in graph references, and supported inherited collections containing both elements and declared members. Named-path reads do not require writing a JSON token scan or building a JSON DOM first. |
| [XmlSerializer (.NET)](https://learn.microsoft.com/en-us/dotnet/standard/serialization/introducing-xml-serialization) | Ordinary XML serialization is not an identity-preserving graph representation. Collection handling serializes elements rather than ordinary additional properties. Construction/member rules, unsupported shapes and cyclic graphs can require wrappers or custom XML handling. | Shared/circular reference entries and collection-plus-member structure, with configurable member selection and developer activators when the target needs nonstandard construction. No XML-specific model mapping is needed for supported shapes. |
| [DataContractSerializer (.NET)](https://learn.microsoft.com/en-us/dotnet/framework/wcf/feature-details/serialization-and-deserialization) | Graph identity is supported, but reference preservation must be enabled. Polymorphic cases can need known-type declarations. Collection contracts and ordinary member contracts are different modeling choices. Choosing binary XML does not add Inheto-style named-path value access. | Graph references in the normal format, compatible-shape reconstruction without the original ordinary class identity, inherited collection members, and direct binary path reads. Inheto does not require a known-source-type registry for ordinary stored object shapes. |
| [DataContractJsonSerializer (.NET)](https://learn.microsoft.com/en-us/dotnet/framework/wcf/feature-details/stand-alone-json-serialization) | Its data-contract JSON mapping is not an identity-preserving graph format; CLR-specific values and polymorphism follow data-contract mappings and known-type rules. Graphs may need reshaping or explicit identity/link handling. | Built-in graph references, native value descriptors and the same addressable collection structure used for selective reads and reconstruction. |
| [BinaryFormatter (.NET, legacy)](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide) | It supports graphs, but couples them to CLR serialization/type contracts and has fundamental security problems; the built-in implementation no longer works from .NET 9. It is not a suitable new dependency. | An independent shape-based format and selective reads, without `[Serializable]` or BinaryFormatter contracts. Construction behavior and optional stored-type controls are explained in [Know your graph](configuration-and-reconstruction.md#know-your-graph). |
| [BinaryReader / BinaryWriter (.NET)](https://learn.microsoft.com/en-us/dotnet/api/system.io.binarywriter) | These are binary I/O building blocks, not object-graph serializers. You must implement layouts, framing, collections, shared identities, cycles, versioning and reconstruction yourself. | The AST, built-in value representations, graph references, collection metadata, reconstruction and path addressing are already provided. |
| [Json.NET / Newtonsoft.Json](https://www.newtonsoft.com/json/help/html/SerializationGuide.htm) | Reference preservation is configurable, not the default. Additional members on collection/dictionary subclasses are normally omitted by their collection contracts; preserving both members and elements needs custom handling or a wrapper. | Supported inherited collections retain both parts, shared/circular references are built in, and direct typed reads work on the binary without first creating a JSON tree. |
| [MessagePack for C#](https://github.com/MessagePack-CSharp/MessagePack-CSharp) | Contractless models are available, but compact integer-key models require assigned keys. Primitive inspection uses a sequential reader rather than an Inheto property-path API. Its standard object encoding is not a built-in identity-preserving cyclic graph representation; reference tracking needs additional modeling/custom formatting. | Native graph references and one path-addressable model for ordinary objects, collections and their inherited members. No assigned integer member keys or separate reference-management layer is needed for supported shapes. |
| [protobuf-net / Protocol Buffers](https://github.com/protobuf-net/protobuf-net) | Stable numeric field contracts must be assigned or modeled. A Protocol Buffers message is not an arbitrary CLR graph with collection inheritance; those relationships need a deliberate message/identity model. | Stored names, native graph links, supported collection inheritance and projection without a separate schema or numeric field declarations. Names still form part of the Inheto application contract; use aliases for deliberate renames. |
| [MemoryPack](https://github.com/Cysharp/MemoryPack) | Ordinary application models normally need `[MemoryPackable]`, `partial` declarations and generated code. Circular-reference and custom-collection behavior use specific generation modes; member ordering/versioning has explicit rules. It already has broad built-in types and multidimensional arrays. | The combination of native type breadth, graph references, supported collection-plus-member shapes and named-path reads without annotating or generating the application model. |
| [FlatBuffers](https://flatbuffers.dev/) | Direct binary access is built in, but normally requires a schema and generated accessors. Mapping arbitrary .NET graphs, collection subclasses and shared identities into that model is application work. | Starts from supported ordinary .NET shapes and exposes named paths, graph links and compatible reconstruction without requiring schema-generated application models. |

For the referenced behaviors, see .NET's [reference-preservation limits](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/preserve-references), [collection contracts](https://learn.microsoft.com/en-us/dotnet/framework/wcf/feature-details/collection-types-in-data-contracts), Json.NET's [reference options](https://www.newtonsoft.com/json/help/html/PreserveObjectReferences.htm), and each project's linked documentation. `SoapFormatter` and `NetDataContractSerializer` are additional legacy .NET formatters, not recommended alternatives; Microsoft's [security guidance](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide) covers them too.

Several alternatives already offer attribute-free objects, rich built-in types, configurable references or selective access. Inheto's advantage for rich .NET graphs is providing these capabilities **together**, including collection inheritance, without a layer of serialization-specific DTOs, converters, reference bookkeeping or schema-generated models for the supported cases. That can remove substantial developer work before serialization and after reading the result.

This is a feature/workflow comparison, not a measured speed ranking. Comparative benchmarks are not yet published. Benchmark equivalent round-trip semantics and actual access patterns when comparing throughput, allocation or payload size. JSON/XML interoperability, Protocol Buffers contracts, and generated-model/AOT tooling can still determine the right choice. Inheto is not wire-compatible with these formats and does not supply their cross-language SDK ecosystems.
